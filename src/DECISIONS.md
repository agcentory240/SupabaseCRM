# Решения и допущения

Документ описывает, что я решил сам там, где ТЗ не даёт однозначного ответа, и что не успел. Это не инструкция по запуску (см. `README.md`), а объяснение хода мыслей.

## 1. Имя пользователя не хранится в `profiles`

**Ситуация:** в ТЗ у задачи есть поля «исполнитель» и «автор», но не сказано, что показывать в UI — email или имя.

**Решение:** храню только `email` и `role`. Отдельного поля `name` нет.

**Почему:** в ТЗ нет требования выводить имя. Email однозначно идентифицирует пользователя и не требует дополнительных полей в форме создания. Если заказчику нужно имя — это одна миграция (`alter table profiles add column name text`) и одно поле в форме.

## 2. История статусов пишется только через SQL-функцию

**Ситуация:** ТЗ требует: «Историю статусов нельзя подделать, изменить или удалить через API».

**Решение:** история пишется **только** внутри `security definer` функции `change_task_status`. Прямой `INSERT` в `task_history` через API невозможен — нет политики на `INSERT` для `authenticated`. На `UPDATE`/`DELETE` прав нет вообще.

**Почему:** просто «скрыть кнопку в UI» недостаточно — ТЗ прямо говорит про обход интерфейса. Функция с `security definer` обходит RLS только для вставки истории, но не даёт пользователю напрямую менять таблицу. Это чуть усложняет код, но гарантирует требование.

## 3. Переходы статусов проверяются на стороне БД

**Ситуация:** ТЗ даёт таблицу переходов и говорит: «Другие переходы запрещены».

**Решение:** проверка переходов — в функции `change_task_status`. Она смотрит текущий статус, роль пользователя и назначение, и бросает исключение при запрещённом переходе.

**Почему:** если проверять только в UI, пользователь может отправить запрос вручную (через консоль браузера или `curl`) и обойти ограничение. Проверка в БД закрывает эту дыру.

## 4. Каскадное удаление

**Ситуация:** ТЗ говорит, что постановщик может удалять объекты. Не сказано, что делать с задачами и историей.

**Решение:** а ничего (смайлик разводящий руками) - потому что удалять связынные записи, которые может уже где то были в отчетах или учтены в других данных - ай ай ай

## 5. Открытая регистрация отключена, тестовые пользователи создаются вручную

**Ситуация:** ТЗ требует: «Открытая регистрация отключена. Тестовых пользователей можно создать вручную в Supabase».

**Решение:** в Supabase отключён «Allow new users to sign up». Три тестовых пользователя создаются вручную в Dashboard с метаданными `{"role": "manager"}` для менеджера.

**Почему:** это прямое требование ТЗ. Ручное создание даёт контроль над ролями и паролями. Триггер `handle_new_user` автоматически создаёт профиль при появлении пользователя в `auth.users`.

## 6. Статусы в БД — на английском, в UI — на русском

**Ситуация:** ТЗ даёт русские названия статусов («Новая», «В работе»...).

**Решение:** в БД храню `new`, `in_progress`, `on_review`, `accepted`, `needs_rework`. В UI — русские подписи через `STATUS_LABELS`.

**Почему:** английские идентификаторы — стандарт для кода (не зависят от локали, не ломаются при смене языка). Русские подписи — только для отображения. Это разделение «данные / представление».

## 7. Тестовые данные

**Ситуация:** ТЗ требует: «В базе — 2–3 объекта и несколько задач в разных статусах».

**Решение:** создаю вручную через UI: 2–3 объекта, задачи в статусах `new`, `in_progress`, `on_review`, `accepted`, `needs_rework`.

**Почему:** это быстрее, чем писать seed-скрипт, и позволяет проверить, что UI и RLS работают на реальных данных. Seed-скрипт можно добавить позже, если понадобится автоматизация.

## 8. Что не успел 

- **Автотесты** (Vitest / Playwright) — не писал. ТЗ не требует, но в проде это было бы нужно.
- **Индексы** на `assignee_id`, `object_id` — не добавлял. Для тестового объёма данных не критично, но при росте стоит добавить.
- **Пагинация** списков — не делал. Для MVP и 2–3 объектов не нужна.
- **Оптимистичные обновления** — не делал. После смены статуса страница перезагружает данные.
- **Обработка ошибок** — базовая (показ текста ошибки). В проде — toast-уведомления и логирование.
- **UI-кит** — используются базовые компоненты Tailwind, без кастомной дизайн-системы. 

## 9. Что бы сделал дальше, если бы было время

1. **Автотесты** на RLS и функцию `change_task_status` — это самая критичная часть, её нужно покрыть.
2. **Индексы** на внешние ключи и `status` — для производительности.
3. **Soft delete** для объектов — чтобы можно было восстановить.
4. **Пагинация** и фильтры в списках.
5. **Уведомления** (например, исполнителю при назначении задачи).
6. **Аудит** — логирование всех действий (не только смены статуса).
